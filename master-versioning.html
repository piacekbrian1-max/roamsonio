Versioning & Rollback

The production safety record for RoamSonio code changes. Every change must have a known-good restore point before work begins, and a failed experiment can never become the new production baseline.

Required Change Protocol

1
Identify the known-good production commit.Before every code change, record the current production SHA and treat it as the restore point. A successful deployment is not automatically a production checkpoint.
2
Record the change.Record the SHA, date/time, exact files being changed, purpose of the change, deployment status and user-test status.
3
Fetch the exact current file SHA before editing.Use the repository's current file content and blob SHA. Never edit from an assumed or stale version.
4
Make one isolated change.Do not combine unrelated architecture, trip-data, UI and destination changes in the same experiment.
5
Compare the result to the restore point.Verify exactly which files and lines changed. Confirm that trip data, IDs, localStorage, Supabase records, routing and existing trip behavior were not unintentionally altered.
6
Deploy and verify deployment.Confirm the GitHub Pages deployment succeeds before asking the user to test. A technically successful deployment still requires user validation.
7
User tests the change.The version becomes a new production checkpoint only after the user confirms the affected functionality and existing trips remain intact.
8
If the test fails: STOP.Do not layer another fix onto a broken version. Revert to the documented restore point, redeploy it, verify the trips are back, and only then investigate the failed experiment separately.
9
Failed experiments never become baselines.A failed deployment or rejected user test remains an experiment. It cannot replace the last known-good production checkpoint.

Checkpoint Definitions

Production checkpointLast version the user tested and approved as working.
Deployment commitLatest code deployed to GitHub Pages. It may still be awaiting validation.
Restore pointExact production commit used to recover after a failed change.

Non-Negotiable Trip Protection

Never trade trip safety for an experiment.
Existing trips must not be overwritten, replaced by a richer copy, regenerated from a template, or lost because of a new feature experiment. When uncertain, preserve the known-good version and stop.
